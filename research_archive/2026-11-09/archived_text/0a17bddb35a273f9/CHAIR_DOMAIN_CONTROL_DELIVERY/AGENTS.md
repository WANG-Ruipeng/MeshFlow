# MeshFlow local execution instructions

## Persistent user preference: resource-aware parallel dispatch

The user explicitly prefers parallel execution of independent experiment work when resources allow. Before every new experiment or new GPU dispatch wave, inspect current resources and choose the concurrency from measurements. Do not automatically serialize all arms, and do not fix a universal worker count.

1. Read `WORKSPACE.md` for the maintained baseline, optional losses, local assets and cleanup history. Keep each experiment's explicit budget, evaluation set and stopping conditions authoritative. Parallel scheduling never authorizes extra arms, updates, samples, calibration or retries.
2. Before dispatch, record GPU name, total/used/free VRAM, GPU compute utilization, active GPU processes, available CPU cores/RAM and relevant CPU/OT/audit load. Use `nvidia-smi` in the actual Windows/WSL environment. Check again before each additional worker and when tasks finish. Do not stop unrelated user processes.
3. Size training, teacher evaluation and sampling separately. Prefer observed peaks from a comparable model, precision, optimizer, face count, batch and loss. Weight-file size and PyTorch peak allocated memory alone are not complete process VRAM estimates: include reserved memory, CUDA context, optimizer/backward and geometry-loss workspaces. Reset/sample peak counters before the measured stage; record their scope.
4. If a comparable peak is missing, start one already-authorized task and observe representative first updates or sampling steps, including backward/optimizer allocation. Do not add unbudgeted GPU probe jobs or synthetic training. Do not infer training memory from inference alone.
5. Initially keep at least max(2 GiB, 10% of total VRAM) of the currently free memory as additional headroom. For comparable new workers, estimate incremental slots as floor(max(0, free VRAM - headroom) / (1.2 * observed per-worker process peak)); also cap by the remaining authorized independent tasks, CPU/RAM availability and any explicit experiment concurrency requirement. These are conservative starting margins, not a hardware guarantee. A zero slot estimate means wait; never force a worker to start.
6. Launch incrementally and remeasure after the prior worker reaches its representative peak. Avoid simultaneous model-loading spikes. Increase concurrency only while measured throughput benefits and the memory headroom holds. Low VRAM occupancy is not the same as low GPU compute utilization; if compute is already saturated, extra GPU workers may not help. CPU matching/OT/offline audit can overlap with independent GPU work when their CPU/RAM budgets allow; limit each process's CPU threads to avoid oversubscription.
7. Parallelize independent arms or pre-registered sample jobs in separate processes with separate output directories and owned model/optimizer instances. Preserve each arm's cloned input stream and independent RNG; sample seeds come from the frozen manifest, never worker ID or completion order. Do not share mutable RNG, model parameters, or a concurrent output writer. Aggregate deterministically by registered identifiers. Preserve stage dependencies, such as 'save all raw before Stage 2'.
8. Keep the audited deterministic runtime: CUBLAS_WORKSPACE_CONFIG=:4096:8 before CUDA initialization; deterministic algorithms enabled with warn_only=False; TF32 disabled; SDPA math; BF16 forward and FP32 parameters/integration. Do not change batch, microbatch, precision, optimizer or sampling definitions just to fit more workers. Existing before/after checks remain required; do not assert repeatability without evidence.
9. Record the dispatch plan and actual worker count, VRAM peaks, throughput and per-phase wall times. Parallel contention changes timing: do not compare concurrent wall time with isolated wall time as if it were the same compute benchmark. Explain why a task remains serial when resource or protocol constraints require it.
10. If memory pressure/OOM or numerical failure occurs, stop dispatching additional jobs, preserve logs and count attempts/updates honestly. Do not kill unrelated processes, silently retry, reduce scientific settings, or exceed the experiment's replay/restart allowance. Follow that experiment's failure contract.

## Current maintenance boundaries

The maintained code is Native T1 + Geo with optional loss recipes. FM remains the default; JEdge5 is explicitly selected by `train-edge5` or `sample --profile edge5`. Pair was retired; its small evidence archive is under `native_t1/maintenance/pair_cleanup_20261002_100559/`. Do not restore its deleted weights or start experiments merely to test scheduling. Official data/weights and retained checkpoints are protected; no automatic Git commit/push.
